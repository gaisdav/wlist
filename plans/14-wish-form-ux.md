# Этап 14. Редизайн экрана создания/редактирования желания

> **Статус: 🔵 план.** Только дизайн-документ — кода нет. Цель — превратить
> [`apps/tma/src/pages/wish-form/WishFormPage.tsx`](../apps/tma/src/pages/wish-form/WishFormPage.tsx)
> (703 строки, одна плоская колонка из ~10 полей) в **прогрессивную, сгруппированную**
> форму, нативную для Telegram Mini App.

## TL;DR

Сейчас все поля — от обязательного «Название» до редкого «Макс. участников
group-gift» — лежат в одной колонке с одинаковым визуальным весом и без заголовков
секций. Пользователь, который хочет «просто добавить желание», вынужден проскроллить
мимо валюты, copy-lines, видимости по спискам, событий и загрузки фото. План: **3 шага
прогрессивного раскрытия** — сначала самое необходимое, остальное под «Подробнее».
Плюс точечные фиксы (безымянная секция copy-lines, валюта, нативная MainButton).

---

## Цель

1. **Снизить когнитивную нагрузку первого создания** — на первом экране только то, без
   чего желание не имеет смысла (название + опционально фото/ссылка/цена).
2. **Сгруппировать** поля по смыслу с заголовками секций, а не выкладывать плоско.
3. **Спрятать продвинутое** (group-gift, видимость по спискам, события, copy-lines) за
   раскрываемые блоки — оно остаётся в один тап, но не мешает в 80% случаев.
4. **Исправить конкретные дефекты** (см. §3), найденные при аудите.

## Не-цель

- Менять модель данных, API, RLS или схему БД. Это **чисто UI/UX-рефактор** одного
  экрана; контракт `ApiClient` и `core` не трогаем.
- Менять `WishDetailPage` (экран просмотра) — кроме того, что он остаётся источником
  правды для copy-формулировок (см. §3.1).

## 1. Что не так сейчас (аудит)

Источник: `WishFormPage.tsx`, рендер начинается на
[стр. 311](../apps/tma/src/pages/wish-form/WishFormPage.tsx#L311). Аудит по
эвристикам Нильсена и Laws of UX.

### 1.1 Плоская простыня без иерархии

Форма — это один `<fieldset>` с 12 блоками `flex flex-col gap-…`, идущими подряд:

```
Название*            ← обязательное
Описание
Цена (опц.)
  └ Валюта           ← появляется только если есть цена
Ссылка (опц.)
[copy-line 1..5]     ← БЕЗ заголовка секции (см. 3.1)
☐ Групповой подарок  ← редкий, продвинутый
  └ Макс. участников
Кто видит это        ← 3 чипа, при «Списки» — ещё выбор списков
События              ← теги + «создать событие»
Фото (опц.)
[Создать желание]
```

**Проблема (Закон Хика):** время на решение растёт с числом и сложностью вариантов.
Здесь 10 равновесных полей, из которых для типичного желания нужны 1–3. Обязательное
«Название» визуально неотличимо от нишевого «Макс. участников group-gift».

### 1.2 Нет визуальных границ секций

`grep` по `<section|border-t|<hr>` в форме → разделителей между смысловыми группами нет
(7 совпадений — это внутренние обёртки, не разделители групп). Глаз не может
сгруппировать «что про цену» vs «кто видит» (нарушение принципа близости Gestalt).

### 1.3 Продвинутое смешано с базовым

`is_collaborative` (групповой подарок со слотами) и `visibility=lists` (выбор
конкретных списков) — это мощные, но **редкие** сценарии. Они занимают столько же
экрана, сколько название. Большинство желаний — обычные, видимые всем.

### 1.4 «Цена» и «Валюта» — два поля вместо одного

Валюта (`hasPrice ? <select>`) появляется отдельной строкой ниже цены
([стр. 383](../apps/tma/src/pages/wish-form/WishFormPage.tsx#L383)). Это два визуальных
скачка (layout shift) и две точки внимания для одного понятия «сколько стоит».

### 1.5 Submit-кнопка внутри формы дублирует нативную MainButton

Этап 13/PR #31 уже добавил `useTelegramMainButton` на этот экран, но in-page
`<Button type="submit">` остался ([стр. 697](../apps/tma/src/pages/wish-form/WishFormPage.tsx#L697)).
Внутри Telegram пользователь видит **две** кнопки «Создать желание» — нативную снизу и
обычную в конце формы. Нужно прятать in-page-кнопку, когда MainButton доступна.

### 1.6 Ошибки видны только после сабмита, плавающая валидация неочевидна

Поля валидируются, но «Списки» с пустым выбором показывает ошибку
`visibility_lists_pick` лишь как мелкий красный текст, а сабмит при этом молча
блокируется тостом ([стр. 219](../apps/tma/src/pages/wish-form/WishFormPage.tsx#L219)).

## 2. Целевой дизайн

### 2.1 Принцип: прогрессивное раскрытие в 3 уровня

| Уровень | Что | Видно по умолчанию |
| --- | --- | --- |
| **1. Суть** | Название*, Фото, Описание, Ссылка, Цена+валюта | да |
| **2. Кто увидит** | Видимость (сегмент-контрол), при «Списки» — выбор | да, но компактно |
| **3. Подробнее** | Текст для копирования (copy-lines), Событие, Групповой подарок | свёрнуто за «Добавить детали» |

«Название» само по себе достаточно для создания желания. Всё остальное —
улучшения, а не требования. **Описание** оставляем на первом уровне (решение по
комментарию: оно помогает дарителю понять желание сразу).

### 2.3 Группировка в секции (с заголовками)

Заменяем плоский `<fieldset>` на семантические `<section>` с `<h2>`-подзаголовками и
тонкими разделителями (`border-t border-border`, нулевой radius — нативно для TG):

```
section "Желание"   → фото + название + ссылка + цена/валюта
section "Видимость" → сегмент-контрол + (условно) списки
<details> "Детали"  → описание + copy-lines + событие + group-gift
```

### 2.4 Сегмент-контрол вместо чипов для видимости

Сейчас видимость — три `badgeVariants`-кнопки (brand/neutral). Для **взаимоисключающего**
выбора правильный паттерн — **segmented control** (как нативный iOS/TG): один трек, три
сегмента, активный подсвечен. Семантически точнее (это radio, не набор тегов) и читается
как «одно из трёх».

```tsx
// Псевдокод компонента-примитива SegmentedControl
<SegmentedControl
  value={visibility}
  onChange={(v) => { setVisibility(v); haptics.select(); }}
  options={[
    { value: 'public',    label: t('wishes.form.visibility_public') },
    { value: 'followers', label: t('wishes.form.visibility_followers') },
    { value: 'lists',     label: t('wishes.form.visibility_lists') },
  ]}
/>
```

`haptics.select()` — лёгкий тик при переключении (паттерн из `apps/tma/src/telegram/haptics.ts`).

### 2.5 Цена + валюта в одной строке

```tsx
<label>Цена (опц.)</label>
<div className="flex gap-2">
  <input inputMode="decimal" className="flex-1 …" {...register('priceStr', { … })} />
  {/* валюта появляется в той же строке, без вертикального скачка */}
  <select disabled={!hasPrice} className="w-28 …" {...register('currency', { … })}>
    …
  </select>
</div>
```

Валюта `disabled` (а не размонтирована) пока цена пуста — нет layout shift, поле
предсказуемо на месте.

## 3. Точечные фиксы (независимы от редизайна)

Эти можно сделать **первым, отдельным маленьким PR** — они полезны сами по себе и
снижают риск большого рефактора.

### 3.1 🔴 Секция copy-lines без заголовка — пользователь не понимает, что это

**Что это поле на самом деле (уточнено).** Это **готовый текст, который дарителю удобно
скопировать в один тап** — номер банковской карты, адрес для доставки, размер/артикул,
ссылка на конкретную модель. Это **не** «что написать на открытке». На экране просмотра
([`WishDetailPage.tsx:215`](../apps/tma/src/pages/wish-detail/WishDetailPage.tsx#L215))
каждая строка рендерится с кнопкой «копировать».

**Сейчас на форме:** блок из textarea с placeholder `«Line 1»` и кнопкой «Add copy line»
([стр. 425](../apps/tma/src/pages/wish-form/WishFormPage.tsx#L425)) — **без заголовка и
без объяснения**, что это и зачем. Старая формулировка `wishes.detail.copy_lines` =
**«What to write on the gift»** вводит в заблуждение → **убираем её и в форме, и в
detail.**

**Фикс — три части:**

1. **Заголовок секции.** Нужен короткий, точный по смыслу «текст для копирования».
   Варианты (выбрать один при реализации):
   - **«Текст для копирования»** — буквально и понятно. *(рекомендую)*
   - **«Что можно скопировать»**
   - **«Данные для дарителя»** — мягче, но менее очевидно про копирование.
   - **«Реквизиты и заметки»** — если хочется охватить и карту/адрес, и размеры.

2. **Инфо-кнопка (ⓘ) рядом с заголовком → bottom sheet** с подробным объяснением и
   примерами. Это снимает длинный hint с самой формы (форма остаётся чистой), а
   любопытный пользователь получает контекст по тапу. Паттерн `BottomSheet` в репо уже
   есть (`apps/tma/src/components/overlays/BottomSheet`).

   ```
   ┌─ Текст для копирования ─────────┐
   │ Добавьте текст, который дарителю │
   │ будет удобно скопировать в один  │
   │ тап на странице желания:         │
   │                                  │
   │  • номер банковской карты        │
   │  • адрес для доставки            │
   │  • размер, цвет, артикул         │
   │  • ссылка на конкретную модель   │
   │                                  │
   │ Совет: в «Описании» можно        │
   │ написать «ниже — данные для      │
   │ перевода», а сами данные вынести │
   │ сюда отдельными строками.        │
   │             [ Понятно ]          │
   └──────────────────────────────────┘
   ```

3. **Placeholder-пример вместо «Line N»** — показывать, *что* сюда писать:
   `напр. «5536 9138 1234 0241»` / `напр. «Москва, ул. …, кв. …»`. Это самостоятельно
   объясняет назначение поля даже без открытия инфо-шита.

**i18n:** удалить/заменить `wishes.detail.copy_lines` («What to write on the gift»);
добавить `wishes.form.copy_lines_label`, `wishes.form.copy_lines_info_*` (заголовок +
тело bottom sheet), `wishes.form.copy_line_placeholder` (пример). См. §4.3.

### 3.2 🟠 Двойная submit-кнопка в Telegram

**Фикс:** прятать in-page `<Button type="submit">`, когда нативная MainButton доступна.
Чистый способ — отдать факт доступности из хука:

```ts
// useTelegramMainButton возвращает, смонтирована ли нативная кнопка
const mainButtonActive = useTelegramMainButton({ … });
…
{!mainButtonActive ? (
  <Button type="submit" isLoading={isSaving}>…</Button>
) : null}
```

In-page-кнопка остаётся фолбэком для браузера/дев-режима (вне Telegram).

### 3.3 🟠 Group-gift: чекбокс → switcher

`is_collaborative` сейчас — чекбокс с текстом «Group gift (others can book slots)» и,
при включении, поле «Max participants». В edit-режиме всё это `disabled` с длинным hint'ом.

**Чекбокс или switcher — что красивее?** Для **бинарного режима, который меняет
поведение** (включил → появляется бронирование слотов) switcher уместнее и
смотрится нативнее в Telegram: чекбокс читается как «отметить пункт в списке», а
toggle — как «включить функцию». Это ровно второй случай. **Делаем switcher.**

```
Групповой подарок                 (•─)   ← toggle справа, метка слева
Несколько человек скидываются —
каждый бронирует слот.
```

**Детали реализации:**
- Новый примитив `Switch` (`components/primitives/switch/`) — доступная кнопка
  `role="switch"` + `aria-checked`, управляется с клавиатуры, уважает
  `prefers-reduced-motion` (без анимации трека). Регистрируется в RHF как `is_collaborative`.
- При включении — раскрывается «Макс. участников» (как сейчас), но как часть блока
  «Детали».
- В edit-режиме toggle `disabled` + hint «нельзя изменить после создания» (поведение
  сохраняется, текущая бизнес-логика не меняется).
- Тактильный отклик при переключении: `haptics.impact('light')`.

> Switch переиспользуем и в других местах (напр. будущие настройки), поэтому это
> примитив, а не локальная разметка.

### 3.4 🟡 Видимость по спискам: пустое состояние

Когда выбрана «Списки», а списков нет — сейчас мелкий текст + ссылка «Manage lists»
([стр. 556](../apps/tma/src/pages/wish-form/WishFormPage.tsx#L556)). Сделать это
`EmptyState`-подобным компактным блоком (примитив `EmptyState` уже есть из PR #31) с
понятным CTA «Создать список».

## 4. Технический план (как, не ломая правила репо)

### 4.1 Новые примитивы (apps/tma)

| Компонент | Где | Зачем |

Все новые — чистый Tailwind + `tailwind-variants`, иконки только `lucide-react`, классы
через `clsx`. Никаких новых зависимостей.

### 4.2 Разбить 703-строчный компонент

`react-hook-form` уже используется — секции получают `register`/`control`/`formState`
через пропсы или `useFormContext`. Состояние (`visibility`, `selectedListIds`,
`selectedEventIds`, `photo`) остаётся в `WishFormPage` и прокидывается вниз.

   себе. Не требует новых layout-примитивов.
2. **PR B — примитивы.** `SegmentedControl`, `Switch`, `FormSection`, `Collapsible` +

4. **PR D — собственно редизайн (§2).** Прогрессивное раскрытие, сегмент-контрол вместо

## 6. Критерии готовности

- [ ] Первый экран формы (create) умещает суть без скролла на типичном телефоне:
      фото, название, описание, ссылка, цена, видимость, «Добавить детали», кнопка.
- [ ] Каждое поле в секции с понятным заголовком; нет полей с одним лишь placeholder.
- [ ] Текст для копирования имеет заголовок + placeholder-пример + инфо-bottom-sheet;
      формулировка «What to write on the gift» удалена везде.
- [ ] Видимость — один сегмент-контрол; при «Списки» выбор раскрывается под ним.
- [ ] Group-gift — `Switch` (не чекбокс); свёрнут в «Детали», раскрывается в один тап.
- [ ] Внутри Telegram видна **одна** кнопка сохранения (нативная), в браузере — in-page.
- [ ] Клавиатура и фокус работают; `prefers-reduced-motion` уважается; контраст ≥ AA.
- [ ] Поведение сохранения/редактирования идентично текущему (тот же payload).
