# Этап 08. Приватность и уровни доступа

> **Статус: 🟡 частично.** Сделан Шаг 1 (схема БД, миграция

## Цель

Дать пользователю гибкое управление видимостью желаний через списки контактов («Семья»,
«Близкие друзья», «Коллеги») и подписчиков. Перевести систему с «всё видно всем
авторизованным» на политику явной авторизации.

## Зависимости

- Этап 05 (соц-функции: подписки, лента).

## Принятые решения (2026-06-29)

Модель сознательно упрощена. Зафиксировано почему:

1. **Видимость желания = `public | followers | lists`.** Режим `private` **убран** — в
   соц-сервисе желание, видимое только автору, не имеет смысла (его место — архив).
   Минус одна ветка в `can_view_wish`.
2. **Никаких «выбранных пользователей» как отдельной сущности.** «Показать конкретным
   людям» моделируется через **список** (`user_lists`); в UI можно дать быстрый выбор
   людей, который под капотом создаёт/переиспользует список. Один механизм → одна ветка
   RLS, один UI, одна таблица связи. Дублирующего режима `users` нет намеренно.
3. **`lists` — несколько списков на желание** (`wish_visibility_lists` M:N). Видимость
   при этом всегда **ровно один режим** (`public`/`followers`/`lists`), т.к. это один
   enum — нельзя смешать `followers` и `lists`.
4. **События — это только теги, без приватности.** Видимость событий **убрана**:
   удаляются `events.visibility` и таблица `event_visibility_lists` (добавленные в Шаге 1).
   Событие остаётся группировкой M:N (`event_wishes`, этап 07); желание может быть в
   **сколь угодно** событиях. Это убирает целый под-этап (видимость событий +
   наследование) — главный источник сложности и путаницы (две независимые оси «кто видит»
   и «как сгруппировано» не пересекаются).
   - Тег события **не раскрывает** скрытое желание: `event_wishes_select` AND-ит
     `can_view_wish`, так что в списке желаний события виден только тот, что тебе доступен.
5. **`is_archived` остаётся ортогонален видимости** — архив прячет «выполненные», но
   видят их по тем же правилам видимости (owner всегда видит свои архивные).

## Скоуп

### 1. Списки контактов (уже в БД — Шаг 1)

- `public.user_lists` (`id`, `owner_id`, `name`, `created_at`, `updated_at`).
- `public.user_list_members` (`list_id`, `member_id`, PK `(list_id, member_id)`).
- RLS: только владелец списка читает/правит свой список и его участников.
- UI: раздел «Мои списки» в профиле — создание, переименование, добавление/удаление.

### 2. Видимость желаний

- `wishes.visibility` (`enum wish_visibility`: `public | followers | lists`, default
  `public`).
- `public.wish_visibility_lists` (`wish_id`, `list_id`, PK) — используется только при
  `visibility = 'lists'` (уже в БД — Шаг 1).

### 3. RLS — пересмотр всех SELECT-политик (ядро этапа)

Единая SQL-функция `public.can_view_wish(viewer uuid, wish_id uuid) returns boolean`
(`security definer`, `stable`):

1. owner (`wishes.owner_id = viewer`) → true (видит и архивные).
2. archived и не-owner → false.
3. `visibility = 'public'` → true.
4. `visibility = 'followers'` → есть строка `follows(follower=viewer, followee=owner)`.
5. `visibility = 'lists'` → viewer состоит в одном из списков из `wish_visibility_lists`
   для этого желания (через `user_list_members`).

Через неё проходят **все** SELECT-политики на wish-зависимых таблицах, **сохраняя**
существующие инварианты:

| Таблица | Текущее правило | Добавляем |
| --- | --- | --- |
| `wishes` | non-archived всем; owner видит свои архивные | `owner OR can_view_wish(...)` |
| `wish_slots` | не-owner (скрытие от автора) | **AND** `can_view_wish` (инвариант скрытия сохраняем) |
| `wish_comments` | гость видит всё; owner — только открытые ветки | **AND** `can_view_wish` (инвариант веток сохраняем) |
| `wish_likes` | все авторизованные | **AND** `can_view_wish` |
| `event_wishes` | все авторизованные | **AND** `can_view_wish` (тег не раскрывает скрытое) |
| `feed_events` | свои + подписки | **AND** видимость subject-желания |
| `storage.objects` (`wish-photos`) | любой авторизованный | **AND** `can_view_wish` (wish id из пути объекта) |

> ⚠️ Эти инварианты — security, не UI. Проверяются RLS-тестами (PR 6).

### 4. Авто-снятие брони при потере доступа

Триггер: когда пользователь теряет доступ к желанию (удалён из списка, на который была
завязана видимость, **или** отписался от автора при `visibility = 'followers'`) и держит
активную бронь `wish_slots` — бронь автоматически переводится в `cancelled`. Охват v1:
**список + отписка**.

### 5. UI

- Селектор видимости (`public | followers | lists`) в форме создания/редактирования
  желания; при `lists` — мультиселект списков пользователя.
- «Мои списки» в профиле (CRUD списков, добавление/удаление участников).
- Индикатор видимости на карточке и деталке — **только владельцу** («Видно: Семье»,
  «Видно подписчикам»).

## Вне скоупа

- Гостевой доступ по ссылке (этап 09).
- Приватность/видимость **событий** (убрана осознанно — см. решения).
- Режим `private` для желаний (убран осознанно).
- Уведомления о добавлении в чей-то список (этап 10).

### PR 5 — RLS test suite (Vitest + supabase-js) — ⏸️ ОТЛОЖЕНО (2026-06-29)

> Решение: пока пропускаем (нет среды для прогона). Дизайн зафиксирован ниже,
> чтобы вернуться без повторного анализа.

**Что тестируем:** owner / follower / list-member / outsider / anon ×
`public|followers|lists` × {wishes, slots, comments, likes, feed, storage}.
Плюс перепроверка инвариантов: owner не видит slots; owner не видит закрытые
ветки комментариев — под каждой видимостью. И триггеры авто-revoke (PR 2):
удаление из списка / отписка снимает активную бронь на ставшее недоступным
желание.

**Среда (рекомендация при возврате): локальный стек + отдельная команда.**

- Тесты создают и удаляют реальных auth-юзеров и строки → гонять только против
  **локального** `supabase start`, НЕ против dev/prod.
- Нужны три вещи: `SUPABASE_URL` (local `http://127.0.0.1:54321`), `anon key`,
  `service_role key` (локальные default-ключи стабильны / печатаются
  `supabase status`).
- Harness: один клиент с `service_role` для сидов (создать профили/желания,
  заполнить `follows` / `user_lists` / `wish_visibility_lists`), и по клиенту с
  `anon` на каждого тест-юзера (через `auth.admin.createUser` + сгенерированную
  сессию или signInWithPassword на сид-юзерах). Каждый кейс: «такой-то юзер
  делает SELECT → видит / не видит ожидаемые строки».
- Запуск **отдельной командой** (`pnpm test:rls`), НЕ в обычном `pnpm test`
  (тот должен оставаться без внешних зависимостей). В CI — отдельный job, который
  поднимает локальный Supabase (как `.github/workflows/supabase.yml` уже умеет
  бутить стек), затем запускает `test:rls`.
- Файлы: вынести в `supabase/tests/rls/*.test.ts` (вне `vitest.config.ts`
  `include`, чтобы не попадали в дефолтный прогон) + отдельный
  `vitest.rls.config.ts`.

**Открытый вопрос на момент возврата:** генерировать сессии тест-юзеров через
admin API vs. password-сиды — выбрать по тому, что проще авторизуется в
supabase-js v2 на локальном стеке.

## Definition of Done

- Можно создать желание, видимое только списку «Семья» (или нескольким спискам), либо
  только подписчикам, либо всем.
- Не-член списка / не-подписчик не видит желание никаким способом (UI, прямой API, фото в
  Storage, лента).
- Существующие инварианты сохранены: автор не видит брони своих желаний; автор не видит
  закрытые ветки комментариев — при любой видимости.
- При удалении пользователя из списка / отписке его активная бронь на ставшее недоступным
  желание снимается автоматически.
