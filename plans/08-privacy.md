# Этап 08. Приватность и уровни доступа

## Цель

Дать пользователю гибкое управление видимостью желаний и категорий — через списки контактов («Семья», «Близкие друзья», «Коллеги»). Перевести систему с «всё видно всем» на политику явной авторизации.

## Зависимости

- Этап 05 (соц-функции).

## Скоуп

### 1. Списки пользователей

Таблицы:

- `public.user_lists`:
  - `id`, `owner_id`, `name`, `kind` (`enum`: `custom` | `family` | `close_friends` | `colleagues`), `created_at`
- `public.user_list_members`:
  - `list_id`, `member_id`
  - PK: `(list_id, member_id)`

UI: раздел «Мои списки» в профиле — создание, переименование, добавление/удаление участников.

### 2. Гибкая видимость желаний

Дополняем `wishes`:

- `visibility` (`enum`: `public` | `followers` | `lists` | `private`, default `public`).

Таблица `public.wish_visibility_lists`:

- `wish_id`, `list_id`
- PK: `(wish_id, list_id)`
- Используется только при `visibility = 'lists'`.

Аналогично — на уровне категории/события (`events.visibility` + связь со списками), чтобы можно было задать видимость целой группе желаний разом.

### 3. RLS — пересмотр всех политик

Это важнейшая часть этапа: **каждая существующая RLS-политика на `wishes`, `wish_slots`, `wish_comments`, `feed_events` (и Storage для фото желаний) должна учитывать видимость.**

SQL-функция `can_view_wish(viewer uuid, wish_id uuid) returns boolean`:

1. Если viewer — owner → true.
2. Если wish.visibility = `public` → true.
3. Если wish.visibility = `private` → false.
4. Если wish.visibility = `followers` → проверить `follows`.
5. Если wish.visibility = `lists` → проверить `wish_visibility_lists` × `user_list_members`.
6. Учесть `is_archived`.

Все RLS используют эту функцию. Это **breaking change**: нужны миграции данных (по умолчанию старым желаниям ставим `public`).

### 4. UI

- Селектор видимости при создании/редактировании желания.
- Управление списками в профиле.
- Индикаторы видимости на карточках и деталке (доступны только автору желания; например, «Видно: Семье», «Видно подписчикам»).

## Вне скоупа

- Гостевой доступ по ссылке (этап 09).
- Уведомления о добавлении в чей-то список (можно добавить в этапе 10).

## Ключевые решения

- **Default `visibility = 'public'`** — по умолчанию желания доступны всем пользователям, а ограничение видимости — выбор автора.
- **Видимость считается одной SQL-функцией** — единая точка правды, нет шанса разойтись между разными RLS.
- **Видимость на уровне события распространяется на все привязанные желания** (если у желания не задана своя — наследует от события).

## Шаги реализации

### Шаг 1. Схема базы данных и миграции
- **1.1.** Создать таблицы `user_lists` и `user_list_members` для управления списками контактов.
- **1.2.** Добавить поле `visibility` (`enum`) в таблицу `wishes` (и в `events` / `categories`).
- **1.3.** Создать таблицу `wish_visibility_lists` для связи желаний со списками.
- **1.4.** Написать миграцию для проставления `visibility = 'public'` всем существующим желаниям.

### Шаг 2. Защита на уровне БД (RLS-политики и триггеры)
- **2.1.** Создать SQL-функцию безопасности `can_view_wish(viewer uuid, wish_id uuid) returns boolean` с полной логикой проверки прав.
- **2.2.** Переписать RLS-политики доступа (SELECT, INSERT, UPDATE, DELETE) для таблиц `wishes`, `wish_slots`, `wish_comments` и `feed_events` с использованием функции `can_view_wish`.
- **2.3.** Добавить триггер в БД: при удалении пользователя из списка контактов (или при отмене подписки), если у него есть активная бронь (`wish_slots`) на желание, к которому он теперь потерял доступ, — **автоматически снимать бронь**.
- **2.4.** Написать SQL-тесты для верификации RLS под разными пользователями.

### Шаг 3. API и React-hooks (Интеграция с Supabase)
- **3.1.** Создать API-методы для управления списками (`createList`, `updateList`, `deleteList`, `addMember`, `removeMember`).
- **3.2.** Обновить методы создания/редактирования желаний, чтобы передавать и сохранять `visibility` и привязанные `list_ids`.
- **3.3.** Создать хуки `useUserLists` для управления списками в UI и `useWishVisibility` для проверки прав.

### Шаг 4. UI: Управление списками контактов в профиле
- **4.1.** Разработать экран «Мои списки» в профиле пользователя.
- **4.2.** Добавить создание/редактирование списков, выбор типа (`kind`: Семья, Близкие друзья, Коллеги, Свой список).
- **4.3.** Сделать удобный мультиселектор подписчиков для добавления/удаления их из списков.

### Шаг 5. UI: Настройка видимости при создании желания
- **5.1.** Интегрировать селектор приватности (`public`, `followers`, `lists`, `private`) в форму создания/редактирования желания.
- **5.2.** При выборе «lists» отображать список доступных групп контактов с чекбоксами для мультивыбора.
- **5.3.** Применить аналогичные настройки приватности для событий/категорий (с поддержкой наследования).

### Шаг 6. UI: Индикаторы видимости и UX-полировка
- **6.1.** Добавить индикаторы приватности (иконки замочка/глазика с подсказкой «Семья», «Приватное» и т.д.) на карточки желаний и на страницу детализации.
- **6.2.** **Важно:** Скрыть показ этих индикаторов от всех пользователей, кроме самого **автора желания**.
- **6.3.** Убедиться, что интерфейс корректно обрабатывает пустые состояния или скрытые элементы в ленте, не допуская JavaScript-ошибок.

## Definition of Done

- Можно создать желание, видимое только списку «Семья».
- Не-член списка не видит желание никаким способом.
- Все существующие тесты RLS обновлены и проходят.

## Открытые вопросы

- Что если пользователя удалили из списка после того, как он забронировал слот? Бронь снимается, а доступ к карточке закрывается.
- Нужно ли «закрытые подписки» (нужно одобрение фолловера)? Пока что нет, фича перенесена в бэклог (см. @[plans/13-future-features.md]).
- Можно ли скрыть само существование желания, или достаточно скрыть его содержимое? Если речь про ограничение видимости желания, то желание скрывается полностью.
