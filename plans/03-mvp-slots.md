# Этап 03. MVP — Слоты совместной покупки

## Цель

Реализовать киллер-фичу сервиса: возможность скинуться на дорогой подарок или собрать средства на нематериальное желание, координируя процесс прозрачно для всех, кроме самого получателя.

## Зависимости

- Этап 02 (Wishlist CRUD).

## Скоуп

### 1. Расширение модели `wishes`

Новые поля:

- `wish_kind` (`enum`: `gift` | `intangible`) — материальный подарок vs «на отпуск/благотворительность».
- `is_collaborative` (`boolean`, default false) — можно ли разделить.
- `slots_total` (`int`, nullable) — фиксированное число участников; `null` = «свободное число».
- `payment_details` (`jsonb`, nullable) — для `intangible`: `{ method: 'card'|'phone'|'iban', value: '...' }`.

### 2. Модель бронирования

Таблица `public.wish_slots`:

- `id` (`uuid`, PK)
- `wish_id` (`uuid`, FK → `wishes.id`, on delete cascade)
- `booked_by` (`uuid`, FK → `profiles.id`)
- `status` (`enum`: `active` | `cancelled`) — отмена не удаляет запись (нужна история)
- `note` (`text`, nullable) — комментарий «я беру это»
- `created_at`, `cancelled_at`

Уникальность: `(wish_id, booked_by) WHERE status = 'active'` — один пользователь не может занять два активных слота на одно желание.

### 3. Бизнес-логика

- **Расчёт статуса желания** (computed на сервере / в SQL view):
  - `open` — есть свободные места (или slots_total = null);
  - `collected` — все слоты заняты (slots_total != null AND active_count == slots_total);
  - `cancelled_just_now` — отдельное событие для уведомлений (см. ниже).
- **Бронирование:**
  - нельзя забронировать собственное желание;
  - нельзя забронировать архивное желание;
  - если slots_total задан и достигнут — блокируем INSERT (через RLS + trigger).
- **Отмена брони:**
  - переводит запись в `cancelled`;
  - триггерит уведомление остальным держателям активных слотов («позиция снова свободна»).

### 4. RLS

- `wish_slots`:
  - **SELECT:** все авторизованные **кроме автора** желания (это «секретная» часть). Автор не должен видеть, кто забронировал.
  - **INSERT/UPDATE:** только сам участник (`booked_by = auth.uid()`).
- Реализация скрытия от автора: RLS-политика с условием `auth.uid() != (select owner_id from wishes where id = wish_id)`.

### 5. Уведомления

В MVP — без Telegram-бота, без push.
- В UI Mini App при открытии экрана желания — fresh-fetch и баннер «слот освободился» (если у пользователя был активный слот, и появилось событие отмены чужого слота).
- Полноценные уведомления — этап 10.

### 6. UI

1. **Карточка желания** теперь показывает:
   - бейдж `Совместная покупка` + индикатор `3/5` или `3 участника`;
   - для нематериальных — реквизиты с кнопкой «копировать».
2. **Кнопка «Забронировать слот»** — для чужих желаний, где `is_collaborative = true`.
3. **Список участников** — кто уже занял слоты (видно всем кроме автора).
4. **«Мои бронирования»** — отдельный экран в профиле.
5. **Форма создания желания** расширяется: тип желания, флаг совместной покупки, кол-во слотов, реквизиты.

### 7. Клиентский слой

- `packages/api`: `slots.list(wishId)`, `slots.book(wishId, note?)`, `slots.cancel(slotId)`, `myBookings.list()`.
- `packages/core`: `useSlots(wishId)`, `useBookSlot()`, `useCancelSlot()`, `useMyBookings()`.

## Вне скоупа

- Telegram-уведомления об освободившихся слотах (этап 10).
- Секретный групповой чат для забронировавших (этап 10).
- Real-time обновление статусов (этап 11).
- Реальная оплата через приложение — её и не будет, мы только координатор.

## Ключевые решения

- **«Скрыто от автора» реализуем строго на RLS**, а не на уровне UI — иначе можно подсмотреть через DevTools/прямой API-запрос.
- **Отмена не удаляет** — нужна история и для аудита, и для будущих фич (рейтинг активных дарителей).
- **Не реализуем платежи внутри приложения** — это базовая ценность концепта (простота + отсутствие финансовой ответственности).
- **`payment_details` как `jsonb`** — гибко на будущее (СБП, IBAN, крипто-кошельки).

## Definition of Done

- Можно создать желание с «совместной покупкой» (фикс или свободное число слотов).
- Друзья могут занимать и отменять слоты.
- Автор желания не видит ни список, ни количество забронированных слотов **через любой способ** (UI, прямой API, REST).
- При достижении лимита желание получает статус `Собрано`.
- Для нематериальных желаний работают реквизиты с копированием.

## Открытые вопросы

- Должен ли автор видеть хотя бы факт «кто-то занял», без имени? (По концепту — нет, всё скрыто. Подтвердить.)
- Что если желание архивировано/удалено, а слот был активен — какое сообщение получает участник?
- Нужно ли разрешать оставлять `note` к слоту в MVP, или это уже излишне?
- Лимит на одного участника: один слот = один человек, или можно занять несколько слотов одного желания?
