# Этап 03. MVP — Слоты совместной покупки

## Цель

Реализовать киллер-фичу сервиса: возможность скинуться на дорогой подарок или собрать средства на желание, координируя процесс прозрачно для всех, кроме самого получателя.

## Зависимости

- Этап 02 (Wishlist CRUD).

## Скоуп

### 1. Расширение модели `wishes`

Новые поля:

- `is_collaborative` (`boolean`, default false) — включена ли совместная покупка (слоты).
- `max_slots` (`int`, nullable) — **верхняя граница** числа занятых слотов (сколько слотов **максимум** может быть занято на это желание). По факту активных строк может быть **меньше**. Если **`null`** — автор не задаёт свой потолок; тогда эффективный потолок **`50`** активных слотов: в UI не предлагаем бронь сверх 50, **и на сервере** (триггер / проверка при INSERT) тот же потолок, чтобы нельзя было обойти клиент. Если **`max_slots` задан** — потолок ровно это число (например `5` → не больше пяти активных строк).
- `copy_lines` (`jsonb`, **nullable**) — **JSON-массив строк** `["…", "…"]` (не `text[]`): до **5** элементов, каждая строка **не длиннее 256 символов** (`CHECK` в миграции + зеркальная валидация в `@wlist/core`). Автор вводит поля при создании/редактировании (реквизиты, адрес одной строкой и т.п.); в UI у каждой непустой строки — **иконка «копировать»** рядом с текстом.

**Не делаем:** отдельного типа/enum «вид желания» (`wish_kind`), отдельного поля `payment_details` с фиксированной схемой — всё произвольное вводится в этих строках.

### 2. Модель бронирования

Таблица `public.wish_slots`:

- `id` (`uuid`, PK)
- `wish_id` (`uuid`, FK → `wishes.id`, on delete cascade)
- `booked_by` (`uuid`, FK → `profiles.id`)
- `status` (`enum`: `active` | `cancelled`) — отмена не удаляет запись (нужна история)
- `created_at`, `cancelled_at`

**Один пользователь может занять несколько слотов** (в том числе все до эффективного потолка): это **несколько строк** с одним и тем же `booked_by` при `status = 'active'`. Уникальность вида «один пользователь — один активный слот» **не** вводим.

Ограничение целостности: для `wish_id` число строк `wish_slots` со `status = 'active'` **не превышает** эффективный потолок **`slot_cap = COALESCE(wishes.max_slots, 50)`** (триггер на INSERT/UPDATE + согласование с RLS). Константу **`50`** дублировать в `@wlist/core` (например `WISH_SLOTS_DEFAULT_CAP`) и использовать в TMA при подсчёте «сколько ещё можно взять».

### 3. Бизнес-логика

Везде, где нужен потолок по слотам, использовать **`slot_cap = COALESCE(wishes.max_slots, 50)`**.

- **Расчёт статуса желания** (computed на сервере / в SQL view):
  - `open` — `active_count < slot_cap`;
  - `collected` — `active_count >= slot_cap`;
  - `cancelled_just_now` — отдельное событие для уведомлений (см. ниже).
- **Бронирование:**
  - нельзя забронировать собственное желание;
  - нельзя забронировать архивное желание;
  - если достигнут `slot_cap` — блокируем INSERT новой активной строки (RLS + trigger).
  - UI: удобный сценарий «взять один / несколько / все оставшиеся слоты» в пределах `slot_cap` (конкретный UX — в макете/итерации).
- **Отмена брони:**
  - переводит запись в `cancelled`;
  - триггерит уведомление остальным держателям активных слотов («позиция снова свободна») — в MVP только задел под этап 10, см. ниже.

### 4. RLS

- `wish_slots`:
  - **SELECT:** все авторизованные **кроме автора** желания (это «секретная» часть). Автор не должен видеть, кто забронировал.
  - **INSERT/UPDATE:** только сам участник (`booked_by = auth.uid()`).
- Реализация скрытия от автора: RLS-политика с условием `auth.uid() != (select owner_id from wishes where id = wish_id)`.

### 5. Уведомления

В MVP — без Telegram-бота, без push.

- В UI Mini App при открытии экрана желания — fresh-fetch и баннер «слот освободился» (если у пользователя был активный слот, и появилось событие отмены чужого слота).
- Полноценные уведомления — этап 10.

### 6. UI

1. **Карточка желания** показывает:
   - бейдж «Совместная покупка» + индикатор занятых слотов, например `3/5` если автор задал `max_slots = 5`, или `3/50` при `max_slots = null` (эффективный потолок 50), либо краткая формулировка в i18n;
   - для непустых `copy_lines` — строки с кнопкой/иконкой **копировать** (без раскрытия содержимого автору в части слотов — только свои строки автор и так знает).
2. **Бронирование слотов** — для чужих желаний, где `is_collaborative = true`; поддержка **нескольких слотов одним пользователем** и «красивый» компактный UI.
3. **Список участников** — кто занял слоты (видно всем **кроме** автора желания).
4. **«Мои бронирования»** — отдельный экран в профиле.
5. **Форма создания/редактирования желания** — флаг совместной покупки, `max_slots` (опционально), до 5 текстовых полей «для копирования» (подпись в UI вроде «Реквизиты / как связаться» — i18n).

### 7. Клиентский слой

- `packages/api`: `slots.list(wishId)`, `slots.book(wishId, …)` (сигнатура под число слотов или повторное бронирование — по выбранному UX), `slots.cancel(slotId)`, `myBookings.list()`.
- `packages/core`: `useSlots(wishId)`, `useBookSlot()`, `useCancelSlot()`, `useMyBookings()`.

## Вне скоупа

- Telegram-уведомления об освободившихся слотах (этап 10).
- Секретный групповой чат для забронировавших (этап 10).
- Real-time обновление статусов (этап 11).
- Реальная оплата через приложение — её и не будет, мы только координатор.

## Ключевые решения

- **«Скрыто от автора» реализуем строго на RLS**, а не на уровне UI — иначе можно подсмотреть через DevTools/прямой API-запрос.
- **Отмена не удаляет** — нужна история и для аудита, и для будущих фич (рейтинг активных дарителей).
- **Не реализуем платежи внутри приложения** — это базовая ценность концепта (простота + отсутствие финансовой ответственности).
- **`max_slots`** — потолок по числу **занятых** слотов-строк; при `null` эффективный потолок **`50`** (UI + сервер).
- **`copy_lines`**: **`jsonb`** = JSON-array строк, **≤ 5** элементов, каждая строка **≤ 256** символов; без отдельной схемы `payment_details`.

## Definition of Done

- Можно создать желание с совместной покупкой и опциональным потолком `max_slots` (или без него — тогда действует лимит **50** слотов).
- Друзья могут занимать и отменять слоты; **один пользователь может держать несколько активных слотов** на одно желание.
- Автор желания не видит ни список, ни количество забронированных слотов **через любой способ** (UI, прямой API, REST).
- При достижении **`slot_cap`** (`COALESCE(max_slots, 50)`) желание получает статус «Собрано» в смысле слотов.
- Строки `copy_lines` отображаются с копированием в буфер обмена.

- Что если желание архивировано/удалено, а слот был активен — какое сообщение получает участник?

**Закрыто (зафиксировано):** `copy_lines` — **`jsonb`** JSON-array строк; **256** символов на строку; при **`max_slots = null`** эффективный потолок **50** слотов — **и в приложении, и на сервере** (триггер).
