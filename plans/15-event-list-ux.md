# Этап 15. UX форм события и списков + общие замечания по приложению

> **Статус: 🔵 план.** Только дизайн-документ — кода нет. Дополняет
> [этап 14](./14-wish-form-ux.md) (форма желания): здесь — форма **события**
> ([`EventFormPage.tsx`](../apps/tma/src/pages/event-form/EventFormPage.tsx)), экран
> **списков контактов** ([`MyListsPage.tsx`](../apps/tma/src/pages/my-lists/MyListsPage.tsx))
> и сквозные замечания по приложению с упором на нативность и лёгкость Telegram Mini App.

## TL;DR

Форма события — компактная (3 поля), её проблемы точечные: один **хардкод-плейсхолдер**
(нарушает правило «только через `t()`»), чекбокс вместо switcher, нет `min` у даты.
Экран списков функционален, но **создание/редактирование вложено и тесно**: создание —
строка «инпут + кнопка» без нативной MainButton; управление участниками — стена кнопок
без поиска; есть **мёртвые i18n-ключи**, один из которых должен был объяснять UX. Плюс
сквозные находки: непоследовательное применение `EmptyState`/haptics, единый `Switch`
напрашивается из трёх чекбоксов.

---

## Цель

1. **Привести формы события и списков к тем же принципам**, что заложены для формы
   желания (этап 14): нативность (MainButton, haptics, `Switch`), понятные секции,
   консистентные пустые/ошибочные состояния.
2. **Закрыть точечные дефекты** (хардкод-строка, мёртвые ключи, отсутствующий `min`
   у даты) — дёшево и сразу.
3. **Свести повторяющиеся паттерны в общие примитивы** (`Switch`, `EmptyState`,
   нативный submit), чтобы экраны не расходились в деталях.

## Не-цель

- Менять модель данных, API, RLS, схему БД. Это **чисто UI/UX**; контракт `ApiClient`
  и `core` не трогаем.
- Дублировать этап 14 — где паттерн уже описан там (`Switch`, прятать in-page submit
  при нативной MainButton), здесь только ссылаемся и переиспользуем.

## 1. Форма события — аудит

Файл: [`EventFormPage.tsx`](../apps/tma/src/pages/event-form/EventFormPage.tsx) (164
строки). Поля: Название*, Дата (опц.), «Повторять ежегодно». Форма короткая и в целом
нормальная — проблемы локальные.

### 1.1 🔴 Хардкод-строка плейсхолдера

[Стр. 128](../apps/tma/src/pages/event-form/EventFormPage.tsx#L128):

```tsx
<input placeholder="e.g. My Birthday" {...register('title')} />
```

Это **единственный** хардкод UI-строки во всём `apps/tma/src` (проверено `grep`).
Нарушает правило проекта «No hardcoded UI strings — everything через `t(...)`»
(CLAUDE.md). Не локализуется.

**Фикс:** ключ `events.form.title_placeholder` → `t(...)`.

### 1.2 🟠 «Повторять ежегодно» — чекбокс вместо switcher

[Стр. 147–156](../apps/tma/src/pages/event-form/EventFormPage.tsx#L147). Это
включение **поведения** («каждый год повторять») — тот же случай, что group-gift в
этапе 14: switcher читается нативнее, чем чекбокс. Используем общий примитив `Switch`
(см. §4.1 этапа 14 и §4 здесь).

### 1.3 🟡 У поля даты нет `min` и нет быстрых пресетов

`<input type="date">` без ограничений ([стр. 141](../apps/tma/src/pages/event-form/EventFormPage.tsx#L141)).
Для **разового** события дата в прошлом обычно бессмысленна.

**Фикс:** `min={today}` для не-повторяющихся (для `is_recurring_yearly` дата года не
важна — оставляем без `min`). **Быстрые пресеты даты не делаем** ✅ — лишняя сложность
для редко используемой формы.

### 1.4 🟡 Нет секций/подзаголовков (мелочь при 3 полях)

При трёх полях группировка не критична, но для единообразия с этапом 14 стоит обернуть
в один `FormSection` «Событие» — тогда оба экрана выглядят из одной системы.

## 2. Экран списков контактов — аудит

Файл: [`MyListsPage.tsx`](../apps/tma/src/pages/my-lists/MyListsPage.tsx) (227 строк,
включая под-компонент `ListMembers`). Экран делает многое: создание списка,
раскрытие, удаление, управление участниками — и оттого плотный.

### 2.1 🟠 Создание списка не использует нативную MainButton

Создание — строка «инпут + кнопка `New list`»
([стр. 164–184](../apps/tma/src/pages/my-lists/MyListsPage.tsx#L164)). На остальных
формах (желание, событие) основное действие уже на нативной Telegram MainButton
(этап 13/PR #31). Здесь — обычная in-page-кнопка, что выбивается из паттерна и
тактильно ощущается «не как в Telegram».

**Решение: «Создать список» → нативная MainButton.** ✅ Действует общее правило проекта:
**submit/основное действие любой формы — всегда на MainButton** (in-page-кнопка остаётся
лишь фолбэком для браузера/дев-режима, прячется при доступной MainButton).

- Кнопка активна (`isEnabled`), когда имя непустое; иначе задизейблена.
- При успешном создании — `haptics.notify('success')` (см. 2.4), поле имени очищается.
- Паттерн скрытия in-page submit — из этапа 14 §3.2.

### 2.2 🟠 Управление участниками — стена кнопок, не масштабируется

`ListMembers` ([стр. 86–110](../apps/tma/src/pages/my-lists/MyListsPage.tsx#L86)):
кандидаты в участники — `flex-wrap` из кнопок `+ Имя`. При десятках
подписок/подписчиков это «облако» кнопок без поиска и без структуры:

```
Добавить участников
[+ Аня] [+ Борис] [+ Вера] [+ Глеб] [+ Дима] [+ ...]   ← растёт неограниченно
```

**Предложение:** компактный список с поиском (как экран `SearchUsers`), каждая строка —
аватар + имя + действие add/remove. Для длинных списков — фильтр по имени сверху.
Текущие участники и кандидаты в одном списке с переключателем состояния (in/out) — это
естественно ложится на тот же `Switch`/чек-строку.

### 2.3 🟠 Мёртвые i18n-ключи — и один из них прячет нужную подсказку

В `lists` определены, но **не используются** в компонентах (проверено `grep`):
`lists.add_members_hint` («Add from people you follow or who follow you.»),
`lists.tab_following`, `lists.tab_followers`.

- `add_members_hint` — это именно та подсказка, которой **не хватает** в секции «Добавить
  участников» (см. 2.2): пользователь не понимает, почему тут именно эти люди. Ключ
  есть — просто не выведен. **Показать его** под заголовком «Добавить участников».
- `tab_following`/`tab_followers` — **удалить ключи.** ✅ Вкладок нет и не планируется;
  словарь не должен содержать неиспользуемых строк.

### 2.4 🟡 Нет тактильного отклика на create/add/remove

Создание списка, добавление и удаление участника — заметные изменения состояния, но
без `haptics`. На фоне лайка/удаления желания (где haptics уже есть, PR #31) это
ощущается «глуше». Добавить `haptics.impact('light')` на действие и
`haptics.notify('success')` на успешный create.

### 2.5 🟡 Пустое состояние списков — бледный `<p>`

[Стр. 187](../apps/tma/src/pages/my-lists/MyListsPage.tsx#L187): «No lists yet…» —
обычный `<p className="text-sm text-muted">`. Примитив `EmptyState` (PR #31) уже есть и
применён на feed/wishlist/bookings — здесь его нет. Привести к единому виду (иконка +
текст; CTA не нужен, т.к. поле создания прямо сверху).

## 3. Сквозные замечания по приложению

Найдено при аудите соседних экранов; не про конкретную форму, но влияет на ощущение
«цельности» и нативности.

### 3.1 🟠 `EmptyState`/ошибки применены непоследовательно

PR #31 ввёл `EmptyState` и применил на feed, my-wishlist, user-wishlist, my-bookings.
Но остались bare-`<p>`:
- [`EventDetailPage`](../apps/tma/src/pages/event-detail/EventDetailPage.tsx) — ошибка
  (`states.error`) и пустой список желаний (`events.detail.empty_wishes`) всё ещё `<p>`.
- [`MyListsPage`](../apps/tma/src/pages/my-lists/MyListsPage.tsx) — пустые списки (2.5).

**Фикс:** добить оставшиеся экраны на `EmptyState` для единообразия (иконка + копирайт
+ при наличии — retry/CTA).

### 3.2 🟠 Три чекбокса → один примитив `Switch`

`type="checkbox"` встречается в трёх местах:
- [`EventFormPage`](../apps/tma/src/pages/event-form/EventFormPage.tsx#L149) — «повторять ежегодно» (§1.2),
- [`WishFormPage`](../apps/tma/src/pages/wish-form/WishFormPage.tsx#L456) — group-gift (этап 14 §3.3),
- [`CommentsBottomSheet`](../apps/tma/src/components/comments/CommentsBottomSheet.tsx#L272) — «показать автору».

Первые два — включение поведения → кандидаты на `Switch`. Третий
(«показать автору») спорный: это согласие в рамках отправки, не персистентная настройка —
**оставить чекбоксом** или сделать switcher по вкусу, но решить осознанно. Главное —
ввести **один** примитив `Switch` (определён в этапе 14 §4.1) и переиспользовать.

### 3.3 🟡 Непоследовательный haptics

`haptics` есть на лайке и destructive-действиях (wish/event delete), но не на:
создании списка/участника (§2.4), сабмите форм (успех create/update),
бронировании слота. Стоит свести к простому правилу:
- `impact('light')` — на тап, меняющий состояние (toggle, add/remove, like);
- `notify('success')` — после успешной create/update/delete мутации;
- `notify('error')` — на отказ мутации.
Вынести в маленький helper-хук поверх `haptics` (`apps/tma/src/telegram/haptics.ts`),
чтобы не дублировать решение в каждом обработчике.

### 3.4 🟡 Native date picker и формат даты

`<input type="date">` рендерит браузерный пикер, который внутри Telegram WebView
выглядит по-разному на iOS/Android. Это приемлемо (нативный для платформы), но стоит
проверить отображение и убедиться, что значение хранится/парсится в одном формате
(`event_date`). Не блокер — пункт для проверки в Telegram-клиенте.

## 4. Технический план

  список» → MainButton). Действует общее правило: submit любой формы — на MainButton.
- **`EmptyState`** (уже есть, PR #31) — для §2.5 и §3.1.

### 4.2 Новые мелкие изменения (только разметка/строки)

| Что | Где | Тип |
| --- | --- | --- |
| `events.form.title_placeholder` + `t()` | EventFormPage | i18n + 1 строка |
| `min` у даты для не-повторяющихся | EventFormPage | атрибут |
| Вывести `lists.add_members_hint` | ListMembers | 1 строка |
| Удалить `lists.tab_following` / `lists.tab_followers` | i18n | чистка |
| `EmptyState` на EventDetail + MyLists | 2 экрана | замена `<p>` |
| `haptics` на create/add/remove | MyListsPage | вызовы |
| «Создать список» → MainButton | MyListsPage | нативный submit |

### 4.3 Поиск участников (§2.2) — отдельный, больший кусок

Переиспользовать паттерн `SearchUsersPage` (фильтр по имени + строки с действием).
Это самый крупный пункт; вынести в отдельный PR, не смешивать с мелкими фиксами.

### 4.4 Что НЕ меняем

- Контракт `ApiClient`, payload `useCreateList`/`useAddListMember`/`useCreateEvent` и т.д.
- snake_case полей, схемы `entities/`, query keys.
- Бизнес-правила (кандидаты = following ∪ followers, и т.п.).
