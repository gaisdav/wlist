# Этап 09. Гостевой доступ по ссылке

## Цель

Дать возможность поделиться вишлистом с теми, кто не пользуется Telegram или не зарегистрирован — чтобы они могли просматривать и бронировать слоты «по имени», без авторизации.

## Зависимости

- Этап 08 (приватность — гостевой доступ это особый уровень видимости).

## Скоуп

### 1. Модель ссылок

Таблица `public.guest_share_links`:

- `id` (`uuid`, PK)
- `slug` (`text`, unique) — короткий URL-friendly идентификатор
- `subject_kind` (`enum`: `wishlist` | `wish` | `event`)
- `subject_id` (`uuid`)
- `owner_id` (`uuid`)
- `expires_at` (`timestamptz`, nullable) — опциональный срок жизни
- `is_revoked` (`boolean`, default false)
- `created_at`

URL: `https://<domain>/g/<slug>` (отдельный публичный SPA-роут, без TMA-обёртки).

### 2. Гостевая идентификация

Гость не имеет аккаунта, но может бронировать. Для этого:

Таблица `public.guest_identities`:

- `id` (`uuid`, PK)
- `share_link_id` (`uuid`)
- `display_name` (`text`) — «Маша из универа»
- `device_token` (`text`) — стабильный идентификатор браузера (cookie/localStorage)
- `created_at`

Расширение `wish_slots`:

- `booked_by` становится nullable
- Добавить `booked_by_guest_id` (`uuid`, nullable, FK → `guest_identities.id`)
- CHECK: ровно одно из двух полей заполнено.

### 3. Гостевой UX

- Открытие `/g/<slug>` → публичная страница с вишлистом, без необходимости логина.
- При первом действии (бронировании) — модалка «Как тебя записать?» → имя → создаётся `guest_identity`, привязывается к токену устройства.
- При повторном входе с того же устройства — узнаёт пользователя по токену.
- Бронирование/отмена работают как у залогиненных.

### 4. Анти-абьюз

- Rate limiting на создание `guest_identities` по IP / per-link.
- Возможность владельца увидеть «Гостевые брони: 3 человека» и удалить любую.
- `is_revoked = true` мгновенно ломает доступ по ссылке.
- (Опционально) код-доступ к ссылке (PIN), не передающийся в URL.

### 5. Преобразование гостя в зарегистрированного

- Если гость потом авторизовался в TMA — предложить «Привязать гостевые брони к аккаунту».
- Реализуется через ввод/сохранение `device_token` или матчинг по `display_name` (опасно).
- В MVP этого этапа — добровольная и явная привязка.

### 6. UI владельца

- Раздел «Ссылки» в профиле — список созданных ссылок, статус, отзыв.
- На карточке wish/wishlist — кнопка «Поделиться вне Telegram».

## Вне скоупа

- Полноценная регистрация без Telegram (отдельная фича в backlog).
- Уведомления гостям (некуда — у них нет канала).
- Гостевые комментарии (умышленно — иначе непонятна модерация).

## Ключевые решения

- **Гость = частный случай слота**, а не отдельная сущность. Это упрощает все экраны «кто забронировал».
- **`device_token` ≠ безопасная идентификация.** Гость может «потерять себя» при чистке кук — это допустимо для MVP-фичи.
- **Скрытие от автора работает и для гостевых броней** — автор не видит, кто из гостей занял слот.

## Definition of Done

- По публичной ссылке без авторизации можно увидеть вишлист и забронировать слот.
- Гость, вернувшийся с того же устройства, узнаётся.
- Автор видит общее число гостевых броней без раскрытия деталей.
- Отзыв ссылки мгновенно блокирует доступ.

## Открытые вопросы

- Гостевой бронь — даём ли её владельцу возможность принудительно отменить?
- Нужно ли требовать электронную почту/телефон для гостевой брони (для контакта в случае проблем)?
- Как уведомить гостя об освободившемся слоте? (Email при наличии, иначе — никак.)
- Стоит ли делать ссылки «одноразовыми» или всегда переиспользуемыми?
