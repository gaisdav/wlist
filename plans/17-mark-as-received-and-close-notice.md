# Этап 17. «Уже подарили» — ручное закрытие желания с уведомлением бронировавшим

## Цель

Дать автору отдельную кнопку «Уже подарили» / «Отметить как полученное» (независимую от
обычного «Архивировать»), чтобы пометить желание как неактуальное для дальнейшего
дарения — с опциональным комментарием, который приходит **персонально** тому(-ым), кто
забронировал/скинулся на это желание. Автор при этом **не узнаёт**, кому именно ушло
сообщение — тот же инвариант приватности, что уже защищает личность бронирующего в
этапе 03.

## Зависимости

- Этап 02 (CRUD, `wishes.is_archived`).
- Этап 03 (Слоты — модель бронирования `wish_slots`, RLS «скрыто от автора»).
- Этап 06 (Комментарии — переиспользуем UI-примитивы вроде модалки подтверждения; сам
  канал доставки — **не** `wish_comments`, см. «Ключевые решения»).

## Скоуп

### 1. Модель данных

- `wishes.received_at` (`timestamptz`, nullable) — момент, когда автор отметил желание
  как полученное. Выставление этого поля **дополнительно** переводит
  `wishes.is_archived = true` (одно действие → два эффекта). Обратное неверно: обычное
  «Архивировать» не трогает `received_at` и не считается «получено».
  Имя колонки — рабочее, финализировать при миграции (кандидаты: `received_at`,
  `marked_received_at`, `gift_received_at`).
- Новая таблица `public.wish_close_notices` (рабочее имя) — отдельный «системный»
  канал, не тред обсуждения:
  - `id` (`uuid`, PK)
  - `wish_id` (`uuid`, FK → `wishes.id`, on delete cascade)
  - `recipient_id` (`uuid`, FK → `profiles.id`) — конкретный бронировавший; одна строка
    на каждого **активного** `booked_by` на момент закрытия
  - `body` (`text`, nullable) — комментарий автора, опционален; лимит длины — см.
    «Открытые вопросы»
  - `created_at`, `read_at` (nullable)
- **Активные `wish_slots` не трогаем** — остаются `active` как историческая запись
  (решение: не отменять автоматически). Желание просто получает `received_at` +
  `is_archived = true`.

### 2. Серверная логика — fan-out без утечки личности автору

SECURITY DEFINER функция/RPC `mark_wish_received(wish_id, comment)`:

- проверяет, что вызывающий — владелец `wish_id`;
- выставляет `received_at = now()`, `is_archived = true`;
- читает список **активных** `booked_by` из `wish_slots` для этого `wish_id` (функция
  имеет право читать эти строки, хотя обычный RLS для владельца их скрывает — тот же
  класс паттерна, что и остальные security-definer помощники в проекте);
- вставляет по одной строке в `wish_close_notices` на каждого `booked_by` с одинаковым
  `body`;
- **не возвращает** вызывающему (автору) список получателей — только факт успеха.

Это зеркало уже принятого в этапе 03 инварианта «автор не видит, кто забронировал»: здесь
автор **пишет** сообщение, но так и не узнаёт, кому конкретно оно ушло.

### 3. RLS

- `wish_close_notices`:
  - **SELECT:** только `recipient_id = auth.uid()` — каждый получатель видит только
    свои уведомления.
  - **INSERT:** запрещён обычным клиентам политикой; строки появляются только через
    `mark_wish_received`.
  - **UPDATE:** только поле `read_at`, только самим получателем (пометка «прочитано»).
- `wishes`: `mark_wish_received` доступна только владельцу (проверка внутри функции).

### 4. UI

- Кнопка «Уже подарили» (финальная копия — по UX) в меню действий желания у
  **владельца**, рядом с «Редактировать»/«Архивировать»/«Удалить» — отдельное действие,
  не подменяет обычный архив.
- По нажатию — модалка/bottom sheet с опциональным полем «Комментарий тем, кто
  бронировал» (например: «Спасибо, уже подарили! ❤️») + кнопка подтверждения.
- Место отображения входящих уведомлений — уже запланированный экран **«Мои
  бронирования»** (`/me/bookings`, этап 03 §6): на карточке своей брони, если по ней
  пришло closing-уведомление, показываем комментарий автора + бейдж «Автор закрыл это
  желание». Отдельный новый экран/раздел в этом плане не создаём.
- Индикатор непрочитанных уведомлений (бейдж/точка) на входе в `/me/bookings» —
  аналогично паттерну unread у комментариев (этап 06).

## Вне скоупа

- Push/Telegram-уведомление о закрытии в реальном времени — зависит от бота (этап 10).
  В этом плане уведомление **сохраняется в БД** и видно при следующем открытии
  `/me/bookings`, но не «выталкивается» пользователю активно.
- Редактирование/отзыв уже отправленного close-комментария автором.
- Разный текст разным получателям — один и тот же `body` уходит всем активным
  `booked_by`.

## Ключевые решения

- **Отдельная кнопка, а не встраивание в архивирование.** «Уже подарили»
  дополнительно архивирует желание, но обычное «Архивировать» не предлагает
  комментарий и не считается «получено» — это осознанно разные действия с разной
  семантикой.
- **Активные слоты не отменяются автоматически** — остаются историческим фактом
  участия.
- **Доставка — отдельная сущность `wish_close_notices`, не `wish_comments`.** Это не
  обсуждение, а одностороннее системное сообщение; заталкивать его в модель веток
  комментариев потребовало бы нового флага-исключения из существующей RLS-модели
  видимости (этап 06) — проще и безопаснее отдельная таблица с собственными узкими
  политиками.
- **SECURITY DEFINER fan-out** — единственный способ доставить сообщение получателям
  без раскрытия их личности автору; развивает уже принятый в проекте паттерн (RLS
  «скрыто от автора» в слотах, этап 03).
- **Push-доставка — вне скоупа, зависит от этапа 10.** Здесь это «почтовый ящик» внутри
  `/me/bookings`, не всплывающее уведомление.

## Чек-лист задач

- [ ] Миграция: `wishes.received_at timestamptz null`; таблица `wish_close_notices`
      (+ индексы по `wish_id`, `recipient_id`)
- [ ] RLS-политики `wish_close_notices` (SELECT/UPDATE только получателем, INSERT
      только через функцию)
- [ ] SECURITY DEFINER функция `mark_wish_received(wish_id, comment)` — owner-check,
      `received_at` + `is_archived`, fan-out по активным `booked_by`, без возврата
      списка получателей автору
- [ ] `pnpm db:codegen` + обновление `core/entities/wish`, новая entity для
      `wish_close_notices`
- [ ] API-слой: `wishes.markReceived(id, comment?)`, `closeNotices.listForMe()`,
      `closeNotices.markRead(id)`
- [ ] Hooks: `useMarkWishReceived()` (invalidate-паттерн — серверная логика, не
      toggle), `useMyCloseNotices()`, `useMarkCloseNoticeRead()`
- [ ] UI: кнопка «Уже подарили» в меню действий + модалка с полем комментария
- [ ] UI: отображение close-уведомлений на карточках `/me/bookings` + бейдж
      непрочитанного
- [ ] Ручная проверка RLS: автор не может прочитать `wish_close_notices` своих
      желаний напрямую через API (SELECT возвращает 0 строк)

## Definition of Done

- Автор может отметить своё желание как «уже получено» отдельной кнопкой, опционально с
  комментарием; желание автоматически архивируется.
- Каждый, кто держал активный слот/резервацию на этом желании, получает персональное
  уведомление с этим комментарием в `/me/bookings`.
- Автор ни через UI, ни через прямой API-запрос не может узнать, кому именно ушло
  уведомление.
- Активные брони/слоты не изменяются при закрытии.

## Открытые вопросы

- Финальное имя колонки (`received_at` / `marked_received_at` / другое) и текст кнопки
  в UI — уточнить при реализации/UX-ревью.
- Лимит длины `body` в `wish_close_notices` — совпадает с лимитом `wish_comments`
  (2000 симв.) или короче (разовое сообщение, не тред)?
- Создавать ли уведомление при пустом `body` (получатель просто видит «желание
  закрыто»), или без комментария уведомление не нужно вовсе?
- Как масштабировать механизм на будущее (этап 10, бот): при появлении push
  `wish_close_notices` естественно становится источником события для рассылки в
  Telegram — проектировать ли таблицу уже сейчас с расчётом на это (например, поле
  `delivered_via_bot_at`)?
