# Этап 06. Скрытые комментарии под желаниями

## Цель

Добавить ветку обсуждения под каждым желанием, **по умолчанию скрытую от автора желания**, чтобы друзья могли координировать выбор подарка без участия получателя. Опционально автор желания видит **целую ветку**, если кто-то при создании корня включил видимость, **или** если **сам автор** начал ветку (его корневые комментарии всегда «открыты» ему под капотом). В открытых ветках автор может писать **корни и ответы** как обычный участник — без чекбокса «показать автору».

## Зависимости

- Этап 05 (соц-функции — профили, подписки, аватары / отображение авторов).

## Скоуп

### 1. Модель данных

Для карточек в ленте и списках без лишних запросов: опционально **`wishes.comments_count`** (`integer not null default 0`) с триггерами на `wish_comments` (increment/decrement при вставке/soft-delete живого комментария). Тогда индикатор «есть обсуждение» на `WishCard` не требует отдельного API.

Таблица `public.wish_comments`:

- `id` (`uuid`, PK)
- `wish_id` (`uuid`, FK → `wishes.id`, on delete cascade)
- `author_id` (`uuid`, FK → `profiles.id`)
- `parent_id` (`uuid`, nullable, FK → `wish_comments.id`) — для тредов первого уровня
- `body` (`text`, 1..2000)
- `is_deleted` (`boolean`, default false) — soft delete
- **`visible_to_owner_thread`** (`boolean`, `not null`, default `false`) — «ветка доступна автору желания». На **корне** (`parent_id is null`):
  - **не-автор** желания — из чекбокса в UI (+ модалка при `true`);
  - **автор** желания — **всегда `true`** (триггер / сервер при INSERT; клиент чекбокс не шлёт).
  На **ответах** — **наследование** от корня ветки; чекбокса в UI нет.
- `created_at`, `updated_at`

### Видимость ветки для автора желания (зафиксировано)

| Сценарий | Поведение |
| -------- | --------- |
| Корневой комментарий **не-автора**, чекбокс **выкл** (по умолчанию) | Автор желания **не** видит эту ветку. |
| Корневой комментарий **не-автора**, чекбокс **вкл** | Автору доступна **вся ветка** (корень + ответы). Перед отправкой — **модалка подтверждения**. |
| **Корневой комментарий автором желания** | В UI — **обычный** новый комментарий (как у всех): `textarea`, отправка. Чекбокса **нет**, модалки **нет**. Под капотом: `visible_to_owner_thread = true` (триггер / сервер). Автор **сразу** видит свою ветку и ответы в ней. |
| Ответ в треде (любой автор строки) | Без чекбокса и без модалки; **наследование** `visible_to_owner_thread` от корня. |
| Редактирование | Чекбокса видимости **нет**; флаг ветки после создания **не меняется** с клиента. |

**UX — кто что видит в форме**

| | Не-автор желания | Автор желания |
| --- | ---------------- | ------------- |
| **Новый корень** | Чекбокс «показать автору» (выкл по умолчанию) + модалка при вкл | Только `textarea` + отправить |
| **Ответ в ветке** | `textarea` + отправить | `textarea` + отправить |

### 2. RLS — критическая часть

- **SELECT (не автор желания):** как раньше — видит все комментарии к `wish_id`, на которые у него есть право участвовать в обсуждении (не автор желания), с учётом soft delete по правилам продукта.
- **SELECT (автор желания):** видит **только** строки, относящиеся к веткам с `visible_to_owner_thread = true` на корне (или эквивалентно — к строкам, у которых после денормализации / вычисления «эффективная видимость ветки» истинна). **Не** видит чужие корни с флагом `false` и всё дерево под ними.
- **INSERT (не автор желания):** `auth.uid() <> owner_id` желания; **корень** — `visible_to_owner_thread` только по чекбоксу (значение с клиента валидируется / перезаписывается триггером); **ответ** — наследование от корня.
- **INSERT (автор желания):** **корень** (`parent_id is null`) на **своём** `wish_id` — **разрешён**; `visible_to_owner_thread` **принудительно `true`** (игнор/перезапись значения с клиента). **Ответ** — в ветке, которую автор **видит** по SELECT (свои корни с `true` + чужие открытые ветки); наследование от корня.
- **UPDATE/DELETE:** только сам **автор строки комментария** (`author_id`); **UPDATE** не должен позволять переключить видимость ветки задним числом.

> ⚠️ Так же, как со слотами — это должно работать **на уровне БД**, а не UI.

### 3. UI

#### Точки входа

- **Деталь желания** — открыть обсуждение (кнопка / строка под стрипом соцсчётчиков).
- **Лента** и **любой список желаний** (мой список, чужой вишлист и т.д.) — та же точка входа на **карточке**, если у желания **есть комментарии** (индикатор по `comments_count` или эквиваленту — см. модель).
- Один и тот же экран обсуждения везде: не дублировать разметку — один контейнер (bottom sheet + содержимое списка/форм).

#### Слой UI: общий `BottomSheet` + доменный `CommentsBottomSheet`

**Решение:** без сторонних drawer-библиотек (Vaul и т.п.) — свой примитив в TMA, переиспользуемый позже (меню действий «Удалить / Редактировать», короткие формы и т.д.).

| Компонент | Путь (ориентир) | Ответственность |
| --------- | ---------------- | ---------------- |
| **`BottomSheet`** | `apps/tma/src/components/overlays/BottomSheet/` | Оболочка: портал в `document.body`, затемнение, панель снизу (`max-h` ~90vh), handle/заголовок, закрытие (overlay, кнопка, Escape; свайп вниз — по возможности в MVP). `role="dialog"`, `aria-modal`, focus trap, **scroll lock** фона. **Не** знает про комментарии. |
| **`CommentsBottomSheet`** | `apps/tma/src/components/comments/` | Домен: `wishId`, `isOwner`, хуки, список тредов, footer с `textarea`. Чекбокс + модалка — **только** `!isOwner` и **новый корень**. У **автора желания** корень и ответ без чекбокса; API/create не полагается на чекбокс для owner. |

API `BottomSheet` (черновик): `open`, `onClose`, `title?`, `children` **или** слоты `header` / `body` / `footer` — чтобы зафиксировать layout «скролл посередине, footer снизу».

**Layout внутри sheet (обязательно для комментариев и пригодно для будущих сценариев):**

```
┌─────────────────────────┐
│ header (title, close)   │  shrink-0
├─────────────────────────┤
│ body                    │  flex-1 min-h-0 overflow-y-auto  ← скролл только здесь
│   …список комментариев… │
├─────────────────────────┤
│ footer                  │  shrink-0, border-t, safe-area
│   textarea + send       │
└─────────────────────────┘
```

- Панель: `flex flex-col` + `max-h-[min(90dvh,…)]`; **не** скроллить всю панель целиком, иначе `textarea` уедет вместе со списком.
- **Footer:** `textarea` (авто-рост до лимита строк — по желанию), кнопка отправки; `padding-bottom: env(safe-area-inset-bottom)`.
- **Клавиатура (TMA / mobile):** при фокусе в `textarea` footer остаётся видимым (при необходимости — `visualViewport` / `scrollIntoView` на footer; не полагаться только на `100vh` в WebView Telegram).
- **Модалка подтверждения** «показать автору» — **поверх** sheet (отдельный лёгкий dialog или второй слой), не ломать scroll body sheet.

**Будущее переиспользование `BottomSheet`:** action sheet (список кнопок без скролла или с коротким списком), подтверждение удаления — тот же примитив, другой `body`/`footer`; не смешивать с `CommentsBottomSheet`.

#### Содержимое `CommentsBottomSheet`

- Список комментариев, форма ответа, поддержка тредов 1 уровня **внутри одного sheet** и на деталке, и со списков.
- Для **не-автора** на карточке/в ленте: при `comments_count === 0` можно **не** показывать кнопку открытия sheet (или показывать «Обсудить» только на деталке — зафиксировать в UI-ревью); если счётчика нет, fallback — иконка/текст после первого комментария.
- Для **автора желания** — в sheet ветки, **открытые ему** (чужие с флагом + **свои** корневые); та же форма: **новый корень** и **ответы** без чекбокса.
- **Корневой комментарий (не-автор):** чекбокс «показать автору» (**выкл** по умолчанию) + модалка при вкл → отправка.
- **Корневой комментарий (автор желания):** обычная отправка; на сервере всегда `visible_to_owner_thread = true`.
- **Ответ (любой):** без чекбокса и без модалки; наследование от корня.
- **Редактирование:** без чекбокса видимости.
- Аватары и юзернеймы.
- Возможность редактирования/удаления своего комментария.
- Маркеры «новых» комментариев с момента последнего просмотра (в т.ч. у автора — только по открытым ему веткам, если показываем).

> Устаревший вариант «вся секция только в теле `WishDetailPage`» заменён на **единый bottom sheet** с точек входа из деталки и списков.

## Вне скоупа

- Упоминания и TG-слой вокруг комментариев (**этап 10** / backlog **13** — см. ссылки выше).
- Real-time появление новых комментариев (этап 11).
- Реакции на комментарии (отдельным backlog-айтемом).

## Ключевые решения

- **Общий `BottomSheet` в `overlays/`** — примитив без доменной логики; layout header / scrollable body / sticky footer; пригоден для комментариев и будущих action sheet.
- **Один `CommentsBottomSheet`** — тот же экран обсуждения с деталки, ленты и списков; внутри — только доменный контент поверх `BottomSheet`.
- **Скрытость от автора по умолчанию + опциональное «открытие ветки» — на RLS.** Любая утечка «закрытой» ветки к автору или наоборот скрытие «открытой» — security-баг.
- **Ветка целиком:** на корне — чекбокс у **не-автора** или **авто-`true`** у **автора желания**; ответы **наследуют**; модалка **только** у не-автора при вкл. чекбокса на корне.
- **Soft delete** — иначе ломаются треды (если удалить родителя, потеряются ответы).
- **Один уровень тредов** — для простоты UX. Глубокие иерархии не нужны.

## Definition of Done

- Автор желания **не** видит закрытые ветки гостей; видит **открытые** и **свои** корневые ветки; может писать **корни** (всегда открыты ему, без чекбокса) и **ответы** в видимых ветках.
- Не-автор: корни с опциональным «показать автору» (+ модалка), ответы с наследованием видимости.
- Обсуждение открывается из **деталки**, **ленты** и **списков** через **один и тот же** bottom sheet при согласованных правилах показа (в т.ч. по `comments_count` на карточке).
