# Этап 05. Социальные функции — подписки, лента, репосты, лайки

## Цель

Превратить инструмент личных списков в социальный сервис: пользователи подписываются друг на друга, видят обновления друзей в ленте, могут «репостить» чужие желания себе и ставить лайки.

## Зависимости

- Этап 02–03 (CRUD желаний, слоты) — стабильная модель `wishes`.
- **Этап 04 (релиз MVP) не блокирует** старт работ по этапу 05: схему БД, API и UI социального слоя можно вести параллельно с полировкой релиза.

## Скоуп

### 1. Подписки

Таблица `public.follows`:

- `follower_id` (`uuid`, FK → `profiles.id`)
- `followee_id` (`uuid`, FK → `profiles.id`)
- `created_at`
- PK: `(follower_id, followee_id)`
- CHECK: `follower_id != followee_id`

RLS:

- **SELECT:** все авторизованные.
- **INSERT/DELETE:** только сам `follower_id`.

API/UI:

- Кнопка «Подписаться/Отписаться» на чужом профиле.
- Счётчики подписчиков/подписок.
- Списки «Подписки» / «Подписчики».

### 2. Поиск пользователей

- Поиск по `username`, `first_name`.
- Возможно — по deep-link `t.me/<bot>?startapp=user_<id>`.
- В перспективе: импорт контактов через Telegram (если разрешит API).

### 3. Лента (Feed)

Таблица `public.feed_events` (event sourcing):

- `id` (`uuid`, PK)
- `actor_id` (`uuid`, FK → `profiles.id`)
- `kind` (`enum`: `wish_created` | `wish_reposted` | `wish_collected` | `slot_booked_public` | `event_created` …)
- `subject_id` (`uuid`) — ID связанной сущности (wish/event)
- `payload` (`jsonb`) — сериализованный снимок данных для рендера
- `created_at`

RLS: пользователь видит только события тех, на кого подписан, плюс свои.

UI:

- Экран «Лента» — бесконечный скролл (cursor-pagination).

Триггеры в БД создают записи `feed_events` при действиях пользователей.

### 4. Репосты

- Поле `wishes.reposted_from_id` (`uuid`, nullable, FK → `wishes.id`, `ON DELETE SET NULL`). После вставки строки значение **не меняется** (триггер в БД).
- **Поток UX:** по кнопке репоста открывается **форма создания желания** (как `/wish/new`) с префиллом полей из оригинала; пользователь правит под себя и сохраняет — создаётся **новое** желание текущего пользователя с заполненным `reposted_from_id`.
- На карточке / в списке **своей копии** **не** показываем индикатор «репост от @username» / автора источника — только обычное желание владельца.
- На карточке и детале **оригинального** желания — **счётчик репостов**: иконка + число (тот же визуальный паттерн, что у лайков). Счётчик = число **неархивных** чужих желаний с `reposted_from_id = id` этого оригинала (прямой репост, без цепочки «репост репоста» в счётчике оригинала — только строки, указывающие на этот `id`).

### 5. Лайки

- Таблица `public.wish_likes`: **`user_id`** (`uuid`, FK → `profiles.id`), **`wish_id`** (`uuid`, FK → `wishes.id`), **`created_at`**; **PK `(user_id, wish_id)`**.
- RLS: чтение строк лайков при той же видимости родительского `wish`, что и для `wishes`; вставка/удаление только от имени `user_id = auth.uid()`; **нельзя лайкнуть своё** желание (`wish.owner_id <> auth.uid()` в политике INSERT).

API/UI:

- Кнопка «сердечко», переключение лайка; отображение количества лайков на карточке/детали.

## Вне скоупа

- Скрытые комментарии (этап 06).
- События/праздники в ленте (этап 07).
- Realtime-обновление ленты (этап 11).

## Ключевые решения

- **Feed как event source** — отдельная таблица, а не computed-выборка из всех таблиц. Это сильно упрощает пагинацию и масштабируемость.
- **Денормализация в `payload`** — храним снимок данных на момент события. Если автор переименует желание, в ленте останется исходный заголовок (это норма для соцсетей).
- **Подписки симметричны** только если оба зафолловили друг друга — взаимная подписка просто не отдельная сущность.
- **Лайки** — нормализованная таблица `wish_likes`, не только счётчик на `wishes`.
- **Репост** — новая строка `wishes` + `reposted_from_id`; без UI-метки «от кого» на копии; метрика на оригинале.

## Definition of Done

- Подписки работают, видны счётчики.
- При создании желания/репосте в ленте подписчиков появляется новая карточка.
- Поиск пользователей работает.
- Можно отредактировать репост в форме и сохранить копию у себя; оригинал показывает число репостов.
- Лайки: toggle и отображение количества.

## Открытые вопросы

- Нужна ли «общая» лента (рекомендации) или только лента подписок?
- Как чистить старые `feed_events` — через TTL? Какой?
- Должны ли быть приватные профили (закрытые подписки), или все профили публичны?

**Закрыто (зафиксировано):** лайки — таблица `public.wish_likes(user_id, wish_id)`; репост — форма редактирования + без индикатора источника на копии; на оригинале — иконка + счётчик репостов.
