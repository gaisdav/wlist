# Этап 05. Социальные функции — подписки, лента, репосты

## Цель

Превратить инструмент личных списков в социальный сервис: пользователи подписываются друг на друга, видят обновления друзей в ленте, могут «репостить» чужие желания себе.

## Зависимости

- Этап 04 (релиз MVP).

## Скоуп

### 1. Подписки

Таблица `public.follows`:

- `follower_id` (`uuid`, FK → `profiles.id`)
- `followee_id` (`uuid`, FK → `profiles.id`)
- `created_at`
- PK: `(follower_id, followee_id)`
- CHECK: `follower_id != followee_id`

RLS:

- **SELECT:** все авторизованные.
- **INSERT/DELETE:** только сам `follower_id`.

API/UI:

- Кнопка «Подписаться/Отписаться» на чужом профиле.
- Счётчики подписчиков/подписок.
- Списки «Подписки» / «Подписчики».

### 2. Поиск пользователей

- Поиск по `username`, `first_name`.
- Возможно — по deep-link `t.me/<bot>?startapp=user_<id>`.
- В перспективе: импорт контактов через Telegram (если разрешит API).

### 3. Лента (Feed)

Таблица `public.feed_events` (event sourcing):

- `id` (`uuid`, PK)
- `actor_id` (`uuid`, FK → `profiles.id`)
- `kind` (`enum`: `wish_created` | `wish_reposted` | `wish_collected` | `slot_booked_public` | `event_created` …)
- `subject_id` (`uuid`) — ID связанной сущности (wish/event)
- `payload` (`jsonb`) — сериализованный снимок данных для рендера
- `created_at`

RLS: пользователь видит только события тех, на кого подписан, плюс свои.

UI:

- Экран «Лента» — бесконечный скролл (cursor-pagination).
- Карточки разных типов событий.

Триггеры в БД создают записи `feed_events` при действиях пользователей.

### 4. Репосты

- Кнопка «Хочу так же» на чужом желании → создаёт копию в своём вишлисте с пометкой `reposted_from_id`.
- Дополнить `wishes` полем `reposted_from_id` (`uuid`, nullable, FK → `wishes.id`).
- В UI карточки — индикатор «Репост от @username».

### 5. Лайки (опционально)

- Простые лайки желаний — для начала просто счётчик и кнопка «сердечко».
- Если решим добавлять, заводим `public.wish_likes(user_id, wish_id)`.

## Вне скоупа

- Скрытые комментарии (этап 06).
- События/праздники в ленте (этап 07).
- Realtime-обновление ленты (этап 11).

## Ключевые решения

- **Feed как event source** — отдельная таблица, а не computed-выборка из всех таблиц. Это сильно упрощает пагинацию и масштабируемость.
- **Денормализация в `payload`** — храним снимок данных на момент события. Если автор переименует желание, в ленте останется исходный заголовок (это норма для соцсетей).
- **Подписки симметричны** только если оба зафолловили друг друга — взаимная подписка просто не отдельная сущность.

## Definition of Done

- Подписки работают, видны счётчики.
- При создании желания/репосте в ленте подписчиков появляется новая карточка.
- Поиск пользователей работает.
- Можно репостнуть чужое желание себе.

## Открытые вопросы

- Нужна ли «общая» лента (рекомендации) или только лента подписок?
- Как чистить старые `feed_events` — через TTL? Какой?
- Должны ли быть приватные профили (закрытые подписки), или все профили публичны?
- Лайки — оставлять или ограничиться репостами?
