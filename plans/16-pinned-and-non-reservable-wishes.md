# Этап 16. Закрепление желаний + желания без бронирования

## Цель

Дать автору два независимых, но родственных инструмента управления своим списком:

1. **Закрепление (pin)** — поднять важное желание наверх списка.
2. **Non-reservable желания** — создать желание (обычной формой), которое **сознательно
   исключено** из потока бронирования/слотов. Кейс: автор хочет что-то сказать
   подписчикам («вы все супер!», номер банковской карты для перевода деньгами), но это
   не то, что нужно/можно «забронировать» как подарок.

Оба флага независимы друг от друга: можно закрепить обычное бронируемое желание,
можно иметь non-reservable желание без закрепления. На практике они часто будут
использоваться вместе (закреплённое объявление наверху списка), но модель не
навязывает эту связь.

## Зависимости

- Этап 02 (Wishlist CRUD) — новые поля на `wishes`.
- Этап 03 (Слоты) — non-reservable напрямую взаимодействует с моделью бронирования
  (`wish_slots`).

## Скоуп

### 1. Закрепление — `wishes.pinned_at`

- Новое поле `wishes.pinned_at` (`timestamptz`, nullable). `null` — не закреплено;
  непустое значение — момент закрепления, используется **одновременно как флаг и как
  ключ сортировки** (решение — не заводить отдельно `is_pinned boolean` + `pin_order
  int`, одного timestamp-поля достаточно).
- **Без верхнего лимита** на число одновременно закреплённых желаний — намеренное
  решение (см. «Открытые вопросы» на случай пересмотра).
- Сортировка в списках (`useMyWishes`, `useUserWishes`, чужой вишлист): закреплённые
  желания — первыми, по убыванию `pinned_at` (последнее закреплённое — выше; то же
  поведение, что у закреплённых сообщений в Telegram-чате); внутри незакреплённых —
  текущий порядок без изменений.
- Toggle: `pinned_at = now()` при закреплении, `pinned_at = null` при откреплении.
  Доступно только владельцу желания.
- UI: пункт «Закрепить» / «Открепить» в меню действий карточки/деталки (только у
  владельца); бейдж «Закреплено» на карточке в списке.

### 2. Non-reservable желания — `wishes.is_reservable`

- Новое поле `wishes.is_reservable` (`boolean`, `not null`, `default true`).
- В форме создания/редактирования — переключатель «Нельзя бронировать» (рабочее имя,
  финальная копия — через `t(...)`). При включении:
  - поля, специфичные для бронирования (`is_collaborative`, `max_slots`), скрываются —
    бронирования не будет вообще, настраивать нечего;
  - `copy_lines` остаются доступны — это и есть основной кейс (номер карты, текст всем
    подписчикам).
- Для желаний с `is_reservable = false`:
  - не-автору не показываются статус резервации (Available/Reserved/`active/cap`) и
    кнопка Reserve / UI слотов;
  - `wish_slots`: **INSERT запрещён на уровне БД** (constraint/trigger + RLS) для
    такого `wish_id`, независимо от клиента — тот же принцип «скрыто/запрещено не
    только в UI», что уже применяется к скрытию слотов от автора (этап 03);
  - на карточке/деталке — визуальный бейдж-индикатор («Объявление» / «Note» — финальная
    копия на UX-ревью) вместо обычного статуса бронирования.

## Вне скоупа

- Отдельная вкладка/раздел «Объявления» в профиле — в этом плане такие желания живут в
  общем списке с бейджем; отдельная группировка — будущее UX-решение.
- Лимит числа закреплённых желаний — сознательно не вводим сейчас.
- Drag-n-drop сортировка внутри закреплённых.

## Ключевые решения

- **`pinned_at` вместо `is_pinned` + отдельного `order`** — одно поле одновременно
  флаг и ключ сортировки.
- **Non-reservable — булево на `wishes`, а не отдельный тип/enum желания** (`wish_kind`)
  — совпадает с принципом этапа 03 («не делаем отдельного типа/enum "вид желания"»).
- **Запрет бронирования проверяется в БД** (constraint/RLS/trigger), а не только
  скрытием кнопки в UI.

## Definition of Done

- Автор может закрепить/открепить любое своё желание; закреплённые желания показываются
  первыми во всех релевантных списках.
- Автор может создать желание с пометкой «нельзя бронировать»; для остальных
  пользователей у такого желания нет ни статуса резервации, ни кнопки Reserve/слотов.
- Прямой `INSERT` в `wish_slots` на non-reservable желание отклоняется на уровне БД
  независимо от клиента.

  список превращается «всё закреплено».
- Финальная копия бейджа для non-reservable («Объявление» / «Note» / другое) — уточнить
  на UX-ревью перед реализацией.
- Нужна ли отдельная группировка non-reservable-желаний (например, всегда внизу списка)
  независимо от `pinned_at`?
